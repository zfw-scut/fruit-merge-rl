# 保留下来的资产与开发经验

## 先把四个时刻分开

这次最容易重走的弯路，是把几个都叫“关键节点”的时刻混在一起。以后设计类似事件时，
建议一开始就分别命名：

- **结构形成点**：让局面开始难以恢复的历史决策；
- **事件显现点（onset）**：检测条件第一次成立；
- **事件确认点（confirmation）**：后续证据足以确认它长期存在；
- **可干预锚点**：替换附近动作确实能改变长期结果的位置。

它们偶尔会重合，但不能默认重合。行为段真正需要的是最后一个，轨迹检测器最擅长给出的是
中间两个。

## 模型开发方面的经验

1. **先写一句能被普通人正确解释的输出语义。**“未来24投放内进入起点”和“当前已经
   堵塞”只差几个字，却对应完全不同的标签、输入、画廊和使用方式。
2. **预测得准不等于归因有用。**在接入反事实系统前，应单独测近期动作替换对事件指标的
   影响，而不是用AP或F1代替因果检验。
3. **保留可重标注的原始场景很值。**这次从未来风险切换到当前堵塞时，无需再次跑大规模
   SAB-128 rollout，就是因为原始曝光、`fruit_id`、onset、confirmation和end都还在。
4. **等级分布必须单独报告。**L7与L11的自然正例率和几何尺度差异很大，宏AP、整体AP和
   统一阈值会讲出完全不同的故事。
5. **时间任务必须画时间序列。**单帧极端样例会放大直觉误读；前置、起点、确认和分类帧
   至少要能相互对照。
6. **轻量模型的工程成功要和路线成功分开。**7,345参数模型训练很快，CUDA吞吐也足够，
   但这不能修复任务定义与反事实需求之间的错位。
7. **不成熟的代理不要提前输入Policy。**这次两个模型都保持只读诊断，避免了任务语义
   变化后还要从策略权重里拆除一个错误输入。

## 给下一位 Agent 的交接清单

如果以后再次研究“严重堵塞”或类似结构事件，先回答下面几个问题：

1. 目标是检测当前失败、预测未来失败，还是定位可干预的历史动作？
2. 标签使用了多少未来信息，在线阶段是否真正拥有这些信息？
3. 事件边界附近替换一两个动作，指标真的会变化吗？
4. 正例率是否按等级、局长和事件身份拆开过？
5. 画廊是否包含事件前、事件起点和确认后的同一对象对照？
6. 新方案能否复用原始场景重新标注，而不急着重新生成几十万局？

本阶段之后提出的“可合成性”更接近结构可达性，而不是当前堵塞分类。但它目前只是下一步
研究方向，不是已确认规格。后续设计应另开新的编号阶段，并先说明它如何给出更靠近可干预
决策的变化节点，不能把本目录直接当作其实现要求。
