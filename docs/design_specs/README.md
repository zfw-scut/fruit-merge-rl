# 当前方案规格

这个目录保存正在讨论、准备实现或等待观察反馈的方案。它的主要作用不是总结过去，而是让
开发者和 Agent 在开始实现前，对“当前选中了什么、哪些地方还没定、什么情况下允许切换”
有同一份参考。

## 与其他文档的分工

- `design_specs/`：现在准备怎样实现，可随审核和观察反馈修订；
- `development_tracks/`：一段开发结束后，复盘需求为什么变化、哪些路线为什么放弃；
- `codex/`：按日期记录实际修改、验证和产物；
- `model_evaluations/`：保存正式模型身份和可复核效果。

设计文档不能代替当前代码和测试；尚未实现的内容也不能用于描述当前接口。

## 使用流程

1. 提出需求，在模块首页拆出需要选择的子方案；
2. 在子技术文档中列出候选路线、边界和易错点；
3. 审核后标记当前选择，再进入实现；
4. 实现后记录实际入口，但先保持“已实现待观察”；
5. 根据人工观察或正式评估，保留当前方案或先修改文档再切换实现；
6. 阶段结束或路线整体弃用后，再在 `development_tracks/` 编写复盘。

## 状态约定

| 状态 | 含义 |
| --- | --- |
| 待讨论 | 只确认了问题，还没有可执行方向 |
| 候选待选择 | 已列出多个方案，尚未决定采用哪个 |
| 暂定采用 | 第一版允许按此推进，但明确等待观察验证 |
| 已确认 | 语义或技术方向已经审核确认 |
| 已选择待实现 | 实现边界已足够清晰，可以进入代码阶段 |
| 已实现待观察 | 代码已完成，但效果和阈值还不能定论 |
| 已验证保留 | 已有足够证据继续使用 |
| 已否决 | 不再按该方案实现 |
| 已被替换 | 保留历史说明，但当前有新的生效方案 |
