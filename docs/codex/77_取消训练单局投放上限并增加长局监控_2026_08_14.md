# 取消训练单局投放上限并增加长局监控

日期：2026-08-14

## 目标与范围

本轮只完成两项修改：

1. 正式训练不再因投放数达到 1000 而结束环境；
2. 定期记录长期存活环境的规模和状态，但不自动终止、刷新或降权。

评估窗口和开局刷新不在本轮范围内，相关实现与规范均未修改。

## 实现

- `TrainingConfig.max_episode_drops` 默认改为 `0`，语义为关闭训练期投放上限；
- 所有正式训练 TOML 的 `[training].max_episode_drops` 改为 `0`；
- 正数上限仍可用于单元测试和小型冒烟；负数配置会被拒绝；
- 阶段标定仍使用独立的 `stage_pilot_max_drops=128`，不会因训练无上限而无限运行；
- 预热状态构造与 Replay 预热改用各自有限预算，不再借用正式训练局上限；
- 训练日志和面板历史新增当前存活局投放数的 mean/P50/P90/P99/max、
  至少 1000/2000/5000/10000 投放的环境占比，以及单环境最大水果槽占用；
- 上述指标只观测，不触发环境重置或其它训练干预。

## 数据规模检查

- 模拟器每个环境仍使用固定 `max_fruits=64` 状态槽，不会随单局投放数增长；
- Replay 是固定容量环形缓冲区，不会因长局持续扩张；
- 最近完成局统计使用 `deque(maxlen=4096)`，日志窗口列表在每次发布后清空；
- 单局训练轨迹没有被整局缓存；常规指标 JSONL 按发布时间增长，而不是按单局长度增长；
- 若某环境真实占满 64 个水果槽，模拟器继续保持现有 fail-fast 行为；本轮通过
  `active_fruit_count_max` 观察该风险，不新增自动恢复路径。

## 验证

- 本地：`tests.test_rl_baseline` 32 项全部通过；
- 格式：`git diff --check` 通过；
- 未在本地运行大规模训练或评估。
