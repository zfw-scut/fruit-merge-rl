# 修复局部 Shapley 文件描述符泄漏

## 修改原因

第一次 250k 正式训练在 update 42348 读取 cold replay 时触发
`OSError: [Errno 24] Too many open files`。服务器的 `nofile` soft limit 为
1024，但模型、CUDA、内存、磁盘和出错 replay segment 均正常。

隔离复现证明：`LocalShapleyTask` 直接提交给 PyTorch multiprocessing 时，默认
`file_descriptor` 共享策略会让任务内每个 `GraphTensor` storage 占用共享 FD。
可信 Shapley 结果又复用原 graph 写入长期因果 replay，因此每个双候选任务稳定留下
约 10 个 FD；累计约 90 个任务后与固定进程池句柄共同触及 1024 上限。

## 主要修改

- Shapley task 在进入 `ProcessPoolExecutor` 前先用 `torch.save` 序列化为普通
  `bytes`，worker 内再恢复成私有 CPU tensor 后运行原 runner。
- 主进程保留的 graph 不再被 multiprocessing 转成共享 storage；因果 replay
  可以继续复用同一 graph，而不会长期持有共享 FD。
- 正式训练 shell 启动器默认把 `nofile` soft limit 提升到当前 hard limit 允许的
  65535，并在 launcher log 中记录实际 soft/hard 值。
- 增加 executor 边界回归测试，并在 Linux 真实 spawn 测试中检查一次 Shapley
  任务不会留下十个 graph storage FD。

update 会重新训练；旧 cold generation 只作为失败现场保留，不参与 hot-resume。
