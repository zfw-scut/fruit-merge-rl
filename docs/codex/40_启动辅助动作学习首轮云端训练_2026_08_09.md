# 启动辅助动作学习首轮云端训练

## 训练目的与证据边界

本轮用于验证辅助动作效果监督、五策略头 bootstrap 和低 epsilon 不确定性探索能否在
24M 训练预算中稳定工作，并与当前 5 层 Fast `score_v1` 基准比较。训练 loss 下降、
吞吐达标或单次训练窗口分数上升都不单独视为策略提升；正式结论仍以相同评估 seed 的
4096 局 30/120 FPS 结果、高等级合成事件和至少一次训练 seed 复现为准。

部署代码为 `baseline-scale-v1` 分支提交 `feb10ec`，通过完整 Git bundle 快进同步到云端。

## RTX 5090 吞吐与显存标定

`【事实】` 初始 1536 环境、batch 384 的 eager 候选端到端吞吐为 3022.19/s，但完整
Replay 显存投影为 33,310.31 MiB，超过 32,109.25 MiB 物理显存，因此禁止用于正式训练。
辅助动作标签让完整 Replay 投影增加约 3,873 MiB，旧模型的环境数和 batch 不能直接照搬。

| 环境 / batch | 模式 | 端到端 transition/s | 完整显存投影 MiB |
| --- | --- | ---: | ---: |
| 768 / 256 | eager BF16 | 2849.18 | 18,861.65 |
| 1024 / 256 | eager BF16 | 2907.37 | 23,523.87 |
| 1280 / 256 | eager BF16 | 2947.76 | 28,402.09 |
| 1024 / 384 | eager BF16 | 2973.20 | 24,583.87 |
| 1024 / 256 | compiled BF16 | 5001.87 | 18,229.87 |
| 1280 / 256 | compiled BF16 | 4913.58 | 21,774.09 |
| 1536 / 256 | compiled BF16 | **5018.34** | **25,366.31** |

`【决策】` 选择 1536/256 compiled BF16。其投影显存约占 79%，低于 85% 门禁；相对
1024/256 的吞吐优势很小，因此训练中若出现显存或稳定性异常，应优先回退至 1024/256，
不再尝试 1792 环境。

## 启动与首批实时事实

正式进程使用以下等价命令后台启动：

```bash
nohup /root/autodl-tmp/venvs/fruit-merge-rl/bin/python -u \
  tools/train_gnn_dqn.py \
  --config configs/gnn_dqn_auxiliary_action_l5_24m.toml \
  --run-dir runs/cloud_rtx5090_auxiliary_action_feb10ec_seed20260809_24m \
  --max-envs 1536 --active-envs 1536 --batch-size 256 \
  > runs/cloud_rtx5090_auxiliary_action_feb10ec_seed20260809_24m/launcher.log 2>&1 &
```

`【事实】` 训练达到 481,792 transition 时状态为：

- 阶段 `training`，Replay 481,792，更新 858 次；
- 实际端到端吞吐约 2458.43 transition/s，ETA 约 2.69 小时；
- GPU 利用率采样 98%，显存约 11,309.94 MiB；
- DQN loss 0.02737，辅助总 loss 0.44096，加权总 loss 0.04942；
- bootstrap 实际激活比例 0.80021，与配置一致；
- epsilon 0.92848，主动学习动作比例为 0，符合只在低 epsilon 阶段开启的设计；
- 未出现 NaN、OOM、训练进程退出或面板失联。

`【事实】` 第二次稳定性检查达到 1,139,200 transition（4.75%），Replay 已装满，累计
更新 3,426 次；实时吞吐约 2510.3/s，GPU 利用率 83%，显存 11.04 GiB，总 loss
0.03977、DQN loss 0.02319、辅助 loss 0.33152，面板消息丢弃为 0，预计剩余约 2 小时
28 分钟。该快照确认训练已经越过预热并进入持续更新阶段。

`【观察】` 正式训练吞吐低于短基准约一半，当前学习器耗时约 4.31 秒，是主要瓶颈。
短基准只用于参数安全筛选，不能替代长时间稳态吞吐；需要在 1M transition 后重新统计
中位吞吐，再决定是否需要下一轮优化 Replay 标签体积或辅助头计算。
