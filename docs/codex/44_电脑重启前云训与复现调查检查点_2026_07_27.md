## 4. CPU / GPU 利用结论

云容器只有 6 个 cgroup CPU：

```text
3 rollout + 1 ordinary CF + 1 Shapley + 1 main
```

角色预算已经全部分配。实测 CPU 平均约 3.7–4.4 核，但约 41% cgroup 周期发生
瞬时节流；主进程 Torch 默认 intra/inter-op 都是 26 线程，形成突发占用和同步空洞。

V100 32 GiB 的整段 GPU 利用率约：

```text
average ≈ 14%
peak ≈ 33%
VRAM peak ≈ 4.2 GiB
```

瓶颈是 CPU StateAnalyzer、EngineSnapshot、图构建、物理 rollout 和跨进程传输，
不是 CUDA 安装错误。首轮 500k 前不要为了“跑满 GPU”临时增大 batch、提高每步更新
次数、增加 rollout worker 或注入未被 config/sidecar 记录的线程环境变量；这些会
改变训练语义或削弱证据可审计性。

## 5. Pymunk 复现调查

ignored 诊断脚本：

```text
runs/audit_cross_process_reproduction.py
```

它使用 fast30、两次 Torch 序列化和持久 spawn worker，复现真实跨进程路径。
当前正式实现、seed 17 的 5000 步结果：

```text
4998 / 5000 strict match
2 / 5000 continuous mismatch
```

两个失败的离散合成语义、ID、顺序、得分、帧数和终止状态仍一致；观测到的边界：

```text
merge event position max error = 0.09749 px
fruit velocity max error = 0.00868
angle/angular-velocity combined max error = 0.000620
```

已经排除的方案：

- `capture_snapshot()` 恢复第一份 blob 后直接返回第一份 blob：没有消除跨进程
  指针哈希噪声，压力测试反而增加分叉，代码尝试已回退。
- 清除 cached arbiters：会改变稳定帧和训练物理语义，而且新碰撞对仍使用 C 指针
  哈希，不能保证确定性；还会造成训练 capture 路径与 eval 路径分布差，不采用。
- 简单放宽现有总 tolerance 后继续生成标签：会把连续噪声与真实语义分叉混在一起，
  不采用。

确认的根因边界：Chipmunk 的 cached arbiter 和新碰撞对哈希包含 C shape 指针；
跨进程恢复后的指针和哈希表枚举顺序不能 bit-exact。高连锁状态可能放大这种顺序差。

下一版应实现三态门禁：

1. `strict_match`
   - 现有完整比较严格通过；
   - 才允许生成 CF / Shapley 标签。
2. `numeric_jitter_drop`
   - frames/stable/done/truncated、merge IDs/等级/顺序/得分、fruit IDs/等级/顺序/
     age/stable 等离散语义全部精确一致；
   - 只存在连续坐标、线速度、orientation 或 angular velocity 偏差；
   - 不生成标签，不计基础设施错误，单独记录数量、比率和各维最大误差。
3. `semantic_divergence_drop`
   - 任一离散语义不一致；
   - 不生成标签，继续进入物理复现失败率；完成结果至少 100 后保持 `<=1%` 门禁。

连续误差必须拆分记录：

```text
merge-event position
fruit position
linear velocity
orientation
angular velocity
```

不能继续用一个 `max_angle_error` 混合 orientation 与 angular velocity。数值抖动率
应使用独立门禁，阈值在 5k 压测数据上冻结；不能复用或稀释语义分叉的 1% 门槛。

1. 先 SSH 读取 `runs/cloud_stage_control/5k_v4_8b30566/status.json`。
2. 若已结束，读取 v4 readiness、`counterfactual_shutdown.json`、

3. 实现上节三态门禁、详细误差字段、checkpoint/shutdown/metrics/readiness 聚合及
   专项测试。
4. 本地跑全量测试，提交新 commit；用 Git bundle 部署云端。
5. 云端跑全量测试和最终配置 preflight。
6. 对保留的旧文件再次执行 `POSIX_FADV_DONTNEED`，从空目录启动修复后的 5k。
7. 5k 全部门禁通过后再启动 10k；不要启动正式 500k。
8. 10k 后更新 `docs/training_runs/FIRST_500K_READINESS.md`，完成最终 commit、
   云端测试和精确 commit preflight。

如果 10k/最终 preflight 需要恢复到至少 80 GiB 可用磁盘，先向用户取得明确的历史
训练大文件删除授权。
