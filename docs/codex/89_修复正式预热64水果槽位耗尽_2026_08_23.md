# 修复正式预热 64 水果槽位耗尽

## 云端门禁事实

6号 RTX 5090 实例已部署 `main@5154607`。SAB-128 teacher 的 `final.pt` SHA-256 为
`fc40b9019c65ecba8502f4334d1418b4f93c0e54e984d42ccc4d0b477bddca07`，与登记身份一致。
CUDA预检通过，确认新learner保持随机初始化，teacher只参与预热场景构造。

真实短跑完成5个候选。旁路激活阶段最快档为2304环境、batch 256，约1972父
transition/s；自动选择器按20%容差内优先低显存的规则推荐1792环境、batch 256，约1777
父transition/s，外部峰值显存占总显存约37.2%。连续2秒GPU采样数量与候选墙钟时间相符；
另行1秒采样观察到有效计算段SM利用率主要为93%～100%。GPU利用率中位数包含编译、预热
和候选切换，不作为选型主指标。

第一次正式启动在分阶段填充262,144条父Replay时以0 transition退出。无缓冲复现日志确认
原因不是CUDA OOM，而是某个预热环境同时存活水果达到固定的64槽容量，下一次投放触发
`max_fruits capacity exhausted`。短标定只填充4096条Replay，因此没有命中该低频边界。

## 修复语义

当前模型、Replay和检查点契约固定为64个水果节点，本轮不把容量扩大到96；扩容会改变图
计算、Replay显存和吞吐标定口径。训练仍保持`max_episode_drops=0`，不恢复按投放次数截断。

当一次投放后某局的同时存活水果数达到64时：

- 该transition以技术终止写入Replay，避免从不可继续表示的状态bootstrap；
- 只重置命中64槽的环境，其余长期环境不受影响；
- 单独累计`capacity_terminated_episodes`，不得与自然死亡混淆；
- 正式评估采用相同容量边界，并在详情中报告容量终止局数。

这属于固定状态表示的硬边界，不是新的投放次数上限。若后续容量终止比例不再稀少，应重新
评估节点容量，而不是继续把它当作普通长期环境。

## 验证

- 修改文件`py_compile`通过；
- `tests.test_rl_baseline`与`tests.test_action_effect_learning`共48项通过；
- 4项CUDA条件测试在本地禁用CUDA时按预期跳过；
- 新测试确认无投放上限时，63槽局面继续运行，64槽局面显式成为episode边界。

以上只确认启动阻塞的原因与代码边界，不构成训练效果结论。修复提交需要重新部署并通过
正式Replay预热门禁后，才能确认正式训练已经运行。
