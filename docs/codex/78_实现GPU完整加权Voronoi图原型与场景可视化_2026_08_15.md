# 实现GPU完整加权Voronoi图原型与场景可视化

## 决策

第一版先实现可观察、可测量的完整GPU参考原型，不直接改训练observation、Replay或Q网络。
场上全部活动水果和桶的左右内壁、底部都参与构图，不按水果等级、埋藏深度或高度裁剪；
顶部保持开放。场景实验室提供独立可视化开关，用于先判断图形语义是否正确。

这里的“完整”指站点全集完整，不把规则采样点当作Space Graph节点，也不声称当前结果是
解析几何精确解。原型从完整GPU距离场恢复动态边和交汇点，后续是否替换为解析拓扑、是否
进入模型，等待视觉审查和训练性能测量后再决定。

## 实现事实

- 新增`WeightedVoronoiGraphBuilder`，接受`[B,N,2]`位置、半径和活动掩码，在CPU或CUDA
  上批量计算圆表面加权距离；空间点到水果站点的距离为`||p-c||-r`。
- 左壁、右壁和桶底作为三个边界站点参与最近距离竞争；顶部只裁剪计算域。
- 默认以4像素间距计算全场距离，按显存预算动态切分空间点，避免批量场景一次生成过大的
  距离张量。
- 距离场只在设备端用于恢复边和交汇节点。API仅返回紧凑线段、交汇点、clearance、owner、
  站点可见样本和统计，不返回规则owner栅格。
- 场景服务新增`POST /api/voronoi/evaluate`、健康状态和构图身份；同一水果几何使用单场景
  最近结果缓存。
- 门户新增默认关闭的“完整加权 Voronoi 图”和“显示空间交汇节点”图层。窄clearance显示
  暖色，宽clearance显示青色；旧场景结果不会覆盖几何已变化的画布。
- 构图触发使用与4像素采样分辨率一致的位置量化键；几何键短时间不变后发起请求，暂停
  场景立即请求。角度、角速度、线速度、队列和分数都不进入Space Graph几何键，并用请求
  前后几何键阻止真正过期的异步结果写回。

## 验证事实

- `tests.test_scenario_lab`共26项通过，覆盖批量图契约、不同半径导致的加权分界移动、
  CPU/CUDA近似一致、紧凑payload、缓存和HTTP接口。
- 门户`npm run lint`与`npm run build`通过。
- 本机RTX 4070 Laptop GPU轻量原型测量：4像素采样、单场40个水果约10.32 ms；16场、
  每场64个水果约416.54 ms，PyTorch峰值显存约238.9 MB。该数字只描述当前原型调用，
  不代表接入训练后的吞吐。
- 场景实验室实际加载“底层缺口”和“同级堆积”预设后，站点、边和交汇点统计随场景更新；
  左右壁、桶底、水果之间的分界与clearance渐变可见，浏览器控制台无错误。
- 修复后使用一局`stable=true`但仍存在阈值内微动的10水果场景复验：无需暂停即可生成
  1178条边和21个交汇点，CUDA构图约35.88 ms。修复前0.25像素位置键会在请求期间因
  微动改变并持续丢弃结果；该问题并非物理稳定状态退化成单帧瞬时速度判定。

## 云端性能测量

2026-08-15在4号实例的RTX 5090上运行4像素采样标准矩阵。输入保持64个定长
水果槽位，分别测试12和56个活动水果；表中是两种活动数的中位数范围。

| 批量 | 距离场 | 完整图 | 完整图吞吐 |
| ---: | ---: | ---: | ---: |
| 1 | 0.42～0.45 ms | 4.28～8.80 ms | 114～234 环境/秒 |
| 16 | 2.63～2.64 ms | 49.93～55.21 ms | 290～320 环境/秒 |
| 64 | 10.64～10.65 ms | 190.41～230.94 ms | 277～336 环境/秒 |
| 256 | 43.14～43.34 ms | 802.62～835.80 ms | 306～319 环境/秒 |

显存不是小批量的主要短板：256环境的最高已分配显存约646.60 MiB，最高保留显存约944 MiB。
距离场在256环境时仅需约43 ms，而完整图需约0.8秒；结合当前实现中按环境恢复
可变长边和交汇点的循环，说明性能主要消耗在拓扑恢复与紧凑化，而不是GPU加权距离场。

另使用真实随机CUDA模拟状态进行同步分段旁路测量：32环境时物理中位数21.01 ms、
构图118.76 ms，保留约15.03%基线吞吐；128环境时分别为26.15 ms和384.60 ms，
保留约6.37%。两档平均只有约8个活动水果，仍已明显拖慢采样。该旁路测量不含Q网络、
Replay和learner，且每阶段显式同步，因此只用于定位构图成本，不视为完整训练吞吐。

随后按项目真正使用过的环境数补测1536、1792和4096环境。每档先预热一次再测量一次，
同样覆盖12和56个活动水果：

| 实际历史环境数 | 距离场 | 完整图 | 完整图吞吐 |
| ---: | ---: | ---: | ---: |
| 1536 | 251.87～253.84 ms | 4.56～4.59 s | 334～337 环境/秒 |
| 1792 | 293.50～296.19 ms | 5.39～5.53 s | 324～332 环境/秒 |
| 4096 | 685.34～687.68 ms | 12.49～12.52 s | 327～328 环境/秒 |

历史档位的真实随机模拟状态平均约8个活动水果。1536、1792和4096环境的旁路构图
分别需4.41、6.11和12.04秒，占同步“物理+构图”阶段时间的99.24%、99.44%和99.72%。
这仍不是完整训练吞吐，但绝对耗时已足以否定当前实现“每环境、每决策构图”的直接接入方式。
4096环境测量的最高已分配显存约5.0 GiB、保留显存约5.3 GiB，单独运行没有OOM，但若与
模型和Replay同驻GPU仍需重新核算显存余量。

标准10个档位和历史9个档位全部通过，没有OOM、超时或非有限状态。原始结果保存在
`benchmarks/results/voronoi_space_graph_20260815/cloud_rtx5090_standard.json`和
`benchmarks/results/voronoi_space_graph_20260815/cloud_rtx5090_historical_envs.json`。当前原型适合继续用于
场景实验室和结构语义验证，但在重写拓扑输出的批处理方式前，不应按每个环境、每次决策
直接接入常规训练。

### 算子级开销分解

2026-08-17增加`profile_voronoi_operator_costs.py`，用未开启profiler的计时保留墙钟基线，
另用PyTorch profiler识别算子调用结构。原4号云实例已拒绝连接，因此算子画像在本机
RTX 4070 Laptop上以8环境、4像素采样执行；该结果只用来解释同一份代码的调用结构，
绝对耗时仍以上述RTX 5090无profiler数据为准。

当前每个环境的拓扑恢复都执行54次动态布尔选取：

- 6种直连侧面组合和4种交汇点到侧面连接，每种分别选取起点、终点、两份clearance
  和owner，共50次；
- 交汇节点的位置、clearance和owner共3次；
- 可见站点统计1次。

每次CUDA布尔索引都需要`nonzero`、为可变长结果确定尺寸，并通常伴随流同步和
Device-to-Host长度回传。8环境profiler实际记录433次`aten::index`、433次`aten::nonzero`、
450次CUDA流同步、442次DtoH拷贝和3408次Kernel launch。其中布尔索引可按代码结构
精确换算为：1792环境约96769次，4096环境约221185次，均包含一次批级半径验证。

在profiler插桩样本中，Kernel发射、流同步、`nonzero`、动态索引和异步拷贝的self CPU
时间合计占插桩运行约70.3%。该比例受profiler本身扰动，只用于定位；但它与RTX 5090上
1792环境的无插桩事实相互印证：距离场约294～296 ms，拓扑恢复与紧凑化约5.10～5.23 s，
分别占完整构图的5.36%～5.45%和94.55%～94.64%。因此主要开销不是Voronoi距离计算，
也不是JSON或前端绘制，而是逐环境、可变长的边和节点提取所造成的高频CPU/GPU调度与同步。

算子原始结果保存在
`benchmarks/results/voronoi_space_graph_20260815/local_rtx4070_operator_profile_4px_b8.json`，统一对比基线保存在
`benchmarks/results/voronoi_space_graph_20260815/traditional_builder_baseline_summary.json`。

### 性能基线记录规则

传统构图和后续轻量网络使用同一口径记录，不把不同层次的耗时混成一个比例：

1. **构图墙钟基线**：在云端实际训练环境数下预热后重复测量距离场、完整构图和
   两者差值；同时记录吞吐、峰值显存和输出图规模。这一层不开profiler，也不计算
   JSON、前端绘制、部署或首次CUDA编译时间，作为速度比较的权威数据。
2. **算子结构画像**：另行记录动态索引、`nonzero`、流同步、DtoH拷贝和Kernel启动次数。
   profiler只用于解释原因，其墙钟时间不与无插桩的传统构图或轻量网络比较。
3. **完整训练占比**：新云实例就绪后，用相同配置、seed和测量步数分别运行正常训练、
   正常训练加距离场、正常训练加完整构图。只有这一层才可用来报告构图占完整训练的
   比例和保留的transitions/s；既有“物理+构图”旁路数据不替代这项测量。
4. **轻量网络对比**：使用同一组几何状态、环境数、硬件和预热方式，分别报告在线推理耗时、
   吞吐和峰值显存。离线教师标签生成时间单独记录，不混入网络在线推理时间；拓扑语义准确性
   也与速度分开验证。

原始运行结果以JSON保留硬件、PyTorch/CUDA版本、算法和源码身份；CSV只作汇总。
当前完整训练占比和轻量网络速度均标记为待新云实例测量，不在本地电脑跑性能结论。

## 当前边界

- 尚未接入训练状态、Replay、模型融合或损失。
- 尚未实现按水果半径分别膨胀障碍后的多尺度可达连通图。
- 尚未把线段链压缩成适合训练批处理的固定上限图；已测旁路构图成本，但尚未接入
  Q网络、Replay和learner测量完整训练吞吐。
- 尚未加入Contact、Mobility、Jamming、Rigidity或针对特定堵塞形态的检测器。
- 4像素采样会带来有限的位置与连接离散误差；先由场景实验室视觉审查决定是否需要更细
  采样或解析拓扑替代。
