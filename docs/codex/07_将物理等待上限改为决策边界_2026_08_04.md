# 将物理等待上限改为决策边界

## 修改原因

一次 `step(action)` 表示相邻两次模型决策之间的物理演化。通常在前一次投放造成的
水果基本稳定后返回；若持续滚动等真实运动一直没有进入稳定窗口，也不能无限等待。
`max_physics_frames=720` 因而是单次决策等待的最大预算，不应被解释为回合结束。

旧实现把跑满预算返回为 `truncated=True` 并设置 `needs_reset`，训练端会丢失仍然
有效的局面，也无法在运动状态上继续投放。本次按确认后的训练语义修正该边界。

## 当前契约

- 达到连续稳定窗口：`stable=True`，本次决策正常返回；
- 跑满 `max_physics_frames` 仍未稳定：`settle_timeout=True`；
- 等待超时时 `done=False`、`truncated=False`、`needs_reset=False`；
- 所有水果的位置、速度、角度、角速度、失败计数和队列状态原样保留；
- 下一次 `step(action)` 直接向仍在运动的世界投放，并继续推进物理；
- 危险线仍可在任何物理帧产生 `done=True`；
- `truncated` 只保留给容量、数值异常等真正的技术回合边界。

奖励和事件仍按动作区间归属：某次 `step` 内发生的合成、分数变化和正式奖励属于
该次转移。等待超时以后延续的运动若在下一次 `step` 中产生合成，则归入下一次
转移。这与“模型在当前状态做出下一次投放决策”的时间边界一致。

## 实现和性能选择

- `BatchPhysicsResult`、`PhysicsResult`、逐帧追踪和回放摘要新增
  `settle_timeout`；
- CPU、CUDA 和 Pymunk 参考环境使用相同离散语义；
- CUDA Kernel 不再把正常的满帧运行写入 `truncated` 或 `needs_reset`；
- Python 批量层依据“启用、帧数到上限、未稳定、未终止、未技术截断”推导
  `settle_timeout`，不增加 CUDA Kernel 参数或额外设备状态；
- 批量训练仍只对 `done | truncated` 执行重置，等待超时无需任何 CPU 同步。

## 验证

契约测试覆盖 CPU 和 CUDA：第一步跑满等待上限后不会要求重置，第二步能够继续
投放，`step_count` 递增且先前水果继续运动。Pymunk/CUDA 分布门禁同时统计
`settle_timeout` 边界差异。随机长局基准额外报告等待超时区间数量和经历过等待
超时的环境数量。

本机 `python-torch` 实测：

- 完整 32 项测试通过；
- 4096 环境乘 20 步为约 72,686 环境步/秒、13,497,942 物理帧/秒，峰值显存
  约 37.74 MiB；
- 64 环境乘 15 步分布门禁中，Pymunk/CUDA 的等待超时次数为 8/5，差值 3；
  得分、合并数和物理帧数相对误差分别约 0.32%、0.52% 和 0.14%；
- 两个后端的 `truncated` 均为 0，证明正常等待超时不再泄漏为回合截断。
- 256 环境连续随机投放 20 次共出现 27 个等待超时间隔、涉及 23 个环境；
  所有 256 个环境仍完成了 20 次投放，且 `truncated_count=0`。
