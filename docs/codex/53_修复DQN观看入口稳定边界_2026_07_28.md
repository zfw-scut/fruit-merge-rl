# 修复 DQN 观看入口稳定边界

## 问题

原观看控制器把 pygame 手动游戏的固定投放冷却当作下一次模型决策边界。冷却结束后，
即使上一颗水果仍在下落或滚动，控制器也会把当前局面以
`stable_boundary=True` 交给 `StateAnalyzer`，再按固定展示延迟投放下一颗。

这不是模型学到的投放时机。正式训练的一个动作包含“投放并推进物理直到连续稳定”，
模型只在稳定边界观察下一状态；原观看时序因此产生训练—推理分布偏移。

## 修复

- `playable_adapter.board_is_stable()` 复用训练的线速度 `35`、角速度 `4` 阈值，
  并在碰撞回调锁定期间拒绝把 Board 当作稳定状态。
- `BoardStabilityGate` 从 checkpoint 读取 `physics_fps` 和 `stable_frames`，先换算
  稳定物理时长，再按真实 Board 的物理帧率累计。正式 fast30 的 `6@30fps` 会对应
  GUI 的 `24@120fps`，而不是错误地只等待 6 个渲染帧。
- 投放、合成、清场等物理拓扑变化会重新累计稳定窗口。决策展示期间若任一水果重新
  运动，pending 动作立即取消，稳定后重新推理。
- pygame 的投放预览可以照常提前出现；`--decision-delay-ms` 仅保留为稳定决策后的
  视觉展示时间。
- 游戏结束和手动重开会同步清理控制器的稳定计数及 pending 动作。

## 验证

- 新增 `tests/test_watch_dqn.py`，覆盖速度阈值、fast30 到 GUI 的 24 帧换算、
  瞬时稳定、拓扑变化、冷却与稳定窗口并行累计、预览期间重新运动、成功投放和跨局
  reset。
- 观看时序测试使用 fake Board，不创建 pygame 窗口。
- 本地全量测试 384 项通过，1 项仅因 Windows 无符号链接权限跳过；0
  failure/error。使用 100K 最佳 H256/L4 推理 checkpoint 和 SDL dummy 的真实
  `DQNBoard` 冒烟运行在 256 个渲染帧内完成 3 次稳定边界决策。
