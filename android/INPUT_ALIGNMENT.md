## 1. 模型输入逐项结论

| ONNX 输入 | Tensor/CUDA 语义 | Android 来源 | 状态 |
| --- | --- | --- | --- |
| `positions` | 固定64槽，圆心x/y，像素，y向下 | `FruitBody.x/y`按原始`slot`写入 | 已对齐；本轮修复旧版压紧槽位 |
| `velocities` | x/y速度，px/s | 同一权威Java物理体的`vx/vy` | 已对齐 |
| `angular_velocities` | 角速度，rad/s | Java物理体角速度 | 已对齐 |
| `levels` | 活动槽1~11，空槽0 | Java水果等级，按固定槽写入 | 已对齐 |
| `physics_radii` | 区分投放半径与合成半径 | `droppedPhysicsRadius`/`mergedPhysicsRadius` | 已对齐 |
| `age_frames` | 每个120 Hz物理帧+1，合成重置0 | Java固定物理子步计数 | 已对齐 |
| `active` | 固定64槽活动掩码 | 真实槽位置1，空槽置0 | 已对齐；本轮修复旧版压紧槽位 |
| `fruit_queue` | q0当前投放，q1~q3未来水果 | Android队列头到尾 | 已对齐；实际游戏随机流与正式seed索引不同，但均为1~5均匀队列 |
| `danger_progress` | `fail_frames / 240`，最新水果不参与圆心越线计时 | 固定物理帧危险计数/240 | 已对齐；本轮从渲染`delta`改为物理帧 |
| `over_danger_line` | 任一水果顶部越过生成线 | `hasFruitTopAboveSpawnLine()` | 已对齐；它与失败计时的圆心规则有意不同 |

模型还固定使用`physics_fps=120`。`score`、`last_score`、`step_count`、水果角度、单颗
`stable`标志、墙钟时间、渲染帧率和推理耗时都不是ONNX输入。

## 2. 决策时间契约

经典AI模式现在逐个固定物理帧维护三个计数：

- 连续稳定15帧后进入下一次决策；
- 单次投放最多推进720帧，未稳定也进入下一次决策；
- 危险计数严格大于240帧时失败，与CUDA Kernel一致。

到达任一决策边界时抓取模型快照，但权威物理世界继续按120 Hz推进，避免异步ONNX推理或
AI手势动画把画面中的水果冻结。若等待期间发生合成，旧决策会失效并在新局面稳定后重新
请求。人工模式和对战模式具有不同的交互规则，不作为正式SAB-T120经典长局分数的等价后端。

## 3. 输入敏感性诊断

`tools/audit_android_input_sensitivity.py`在seed `42000000`的1000个真实Tensor/CUDA决策
状态上运行；基准局得分11407。以下结果只表示模型对字段变化的局部敏感性，不把Java长局
分差归因给某一个字段。

| 变体 | 动作翻转 | 翻转率 | 单步最大Q差均值 |
| --- | ---: | ---: | ---: |
| 所有活动水果年龄 +1帧 | 0 / 1000 | 0.0% | 0.000073 |
| 所有活动水果年龄 +5帧 | 1 / 1000 | 0.1% | 0.000361 |
| 所有活动水果年龄 +10帧 | 2 / 1000 | 0.2% | 0.000715 |
| 危险进度 +1/240 | 2 / 1000 | 0.2% | 0.006086 |
| 危险进度 +5/240 | 12 / 1000 | 1.2% | 0.030565 |
| 危险进度 +10/240 | 23 / 1000 | 2.3% | 0.061503 |
| 旧版固定槽压紧 | 9 / 1000 | 0.9% | 0.000210 |

结论：10帧年龄差会影响少量低间隔决策，但不足以单独解释当前长局均分差；危险进度和
固定槽位也必须严格对齐。修正桌面Java评测器的槽位编码后，原32局结果逐局完全不变，仍为
均分5997.22、中位4122、27局失败，说明该32局中槽位压紧不是分差来源。

随后以CUDA Kernel为唯一规格逐表达式复核，发现Android投放水果初始`vy=0`，而CUDA为
`80 px/s`；实际APK还曾把物理圆心放在预览悬浮高度，而非`spawn_y=252`。两项均已直接
修正，碰撞与冲量计算也恢复为CUDA源码的运算顺序。相同32个seed重新闭环评测后，均分由
5997.22提高到6795.84，中位数由4122提高到6753.50，局均投放由549.97提高到616.06。

上述两组历史Java闭环结果运行时，新投放尚未像CUDA的`perform_drop=true`一样清空全场
`quietFrames`，因此只保留为当时Java实现的相对结果，不再作为当前Android与CUDA严格对齐
后的最终分数。旧版实时Android还逐画面帧把物理`delta`截断到50 ms，设备低于20 FPS时会
丢失物理时间；桌面闭环固定逐次推进`1/120`秒，不经过该实时路径。

## 4. 仍需真机验证的边界

- 尚未从Android ARM设备导出逐决策输入张量和动作校验和；
- ONNX在已保存Tensor/CUDA 1000步轨迹上动作完全一致，但仍需记录真机推理p50/p95延迟；
- Java与CUDA碰撞求解的连续状态仍会逐步分叉；本次输入对齐不宣称两套物理逐位相同；
- 存档格式已升级并保存真实物理槽位，旧开发期schema 1存档会按现有版本门禁失效。

下一项有效证据应是真机逐决策张量导出，而不是继续根据画面或最终分数猜测输入差异。
